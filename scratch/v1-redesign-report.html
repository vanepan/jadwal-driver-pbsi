What shipped, what didn't, and why the line sits where it does

A phase-by-phase account of implementing the "Sarpras V1 Redesign Implementation Map" design project against the live Sarpras Operations codebase, across three work passes: token unification, a shared component library, an app-shell retarget that turned into an app-wide dark-mode sweep, the Assignment Board's mobile List view and filter chips, a 5-tab restructure of the Vehicle detail drawer, and a systematic audit — re-verified a second time on request — of every remaining module against the design map's own per-module spec. Every change was grep-audited before touching a file and verified in a headless browser, in both themes, afterward.

How the work actually unfolded

Two passes, and where the line sits now

Pass 1 built the foundation and fixed the Assignment Board's two pre-vetted gaps. Pass 2 finished the Assignment Board's mobile parity and filter chips, restructured the Vehicle detail drawer into the design map's 5-tab shape, and audited every remaining module against its own spec — most were already compliant, one raised a genuine data-model question instead of a visual one.

01Foundation

Tokens: one accent, one shadow scale, one status palette

The app had three-to-four parallel color systems — a legacy style.css palette, platform.css's intended-but-underused V2 scale, a "card system" copy-pasted into four different files, and a separate crimson pair for Overtime/Petty Cash. The design map's own migration strategy calls for landing tokens first and deleting the competing systems in the same pass — not inventing a fifth.

1a — Extend the canonical scale Shipped

Added the tokens the design map calls for that didn't exist yet: three more type-scale steps, a real 8px spacing scale, four motion durations, five breakpoint custom properties, and --accent-hover/--accent-subtle.

Grep-verified zero existing consumers for every new name before adding it — pure addition, zero visual change. Deliberately excluded a radius scale: --radius-sm/--radius-lg already have 30+ consumers elsewhere with inconsistent or missing fallbacks, so defining them at :root would have been a real, uncontrolled visual change, not an addition.

File
platform.css

1b — Retire the duplicate systems Shipped

Aliased the "card system" copy (Gudang, Engineering, Analytics) and the Overtime/Petty Cash crimson pair onto the canonical --accent/--info/--ok/--warn/--danger/--shadow-* tokens, one brand color and one shadow scale app-wide. Kept genuinely categorical colors with no canonical equivalent — Engineering's live violet/teal/neutral category tags — untouched rather than force-mapping them onto something semantically wrong.

Files
gudang.css, engineering.css, overtime.css, petty-cash.css, platform.css (.v2-analytics-claude)

2 — Shared component library Shipped

Extended the existing .p-* utility namespace with the primitives the design map's component list was still missing: secondary/tertiary/icon button variants with a real 44px touch target, a removable chip, a de-boxed card (plus a --boxed legacy escape hatch), a table shell, a generic nav item, underline tabs, a capped KPI strip, and an error state to sit alongside the existing empty state.

Additive only — nothing existing was rewired to consume these yet. Module-by-module adoption is deliberately separate, later work.

02Shell & Home

The app shell, and the sweep it turned into

Retargeting the sidebar and header onto canonical tokens surfaced something bigger than the shell: style.css's own --dark/--white/--red family — never remapped for dark mode — is read in 129 places across the whole app, not just the shell. Fixing the shell properly meant fixing all of it, since the fix is identical everywhere it appears.

3 — Shell chrome Shipped

Retargeted .sidebar, .header, .role-badge, and related selectors onto --side-bg, --topbar-bg, --accent, etc.

Most of what looked like live bugs turned out to already be fixed — platform.css loads after style.css and already overrides .header, .sidebar, .sidebar-nav-primary, .sidebar-badge, and .role-badge with these exact tokens. I corrected my own "bug fix" comments to say so honestly rather than let the false claim stand. The two fixes that were real and previously unfixed: .brand-title and .sidebar-toggle:hover, both reading the un-bridged --dark token with no override anywhere.

File
style.css

3b — Home workspace widgets Audited, no change needed

js/workspace/* and js/widgets/* were built later (v1.19.9) and already read canonical or properly-scoped tokens exclusively — zero legacy-token references found. .wsp-card independently already implements the same de-boxed philosophy the new .p-card encodes.

3c — App-wide dark-mode + touch-target sweep Shipped

Systematically found and fixed every remaining site: --dark/--dark-2 (38 sites, always text — bulk-replaced to --text), --white used as a surface background (20 sites — bulk-replaced to --surface, with one deliberate exception kept: the toggle-switch knob, which is meant to stay white on its colored track, matching platform.css's own equivalent), and the --red/--red-mid/--red-light family (51 sites, individually judged as either brand/CTA → --accent, or alert/status → --danger).

Also closed the exact touch-target gap the design spec named: .btn-primary, .btn-secondary, .btn-danger, .btn-success, and .btn-today had no min-height at all — effective height was around 34px, and .btn-today shrank to roughly 30px on mobile.

Every color: var(--white) site left in the app was individually checked and confirmed to be legitimate text-on-colored-surface (badges, avatars, timeline blocks) rather than the surface-background bug pattern, so none of those needed touching.

03Flagship module

Assignment Board — from two fixes to full parity

Pass 1 shipped the guardrails doc's one pre-vetted gap. Pass 2 came back for the rest of what §4c called for and found a real, code-confirmed bug along the way: the mobile breakpoint didn't just fail to redesign the List-view toggle — it hid it completely, with no substitute. The one item still not built (a net-new vehicle-lane view) was explicit in the brief as optional, not required.

4a — Hardcoded vehicle legend + form select Shipped

A 5th or 6th vehicle in the fleet used to never appear in the timeline legend or the assignment form's vehicle dropdown — both were static markup naming exactly four vehicles. Both now read getActiveVehicles() live, mirroring the driver-select pattern that already existed for exactly this purpose.

Verified end-to-end in a browser: in the unauthenticated fallback path, legend and dropdown render byte-identical to the old hardcoded markup (same four vehicles, same colors, same order) — zero regression — and the code path for a live, authenticated session is the same one already proven correct for the driver dropdown.

Files
index.html, js/drivers.js, js/app.js

4b — Title tooltip + passive conflict badge Shipped

Assignment titles truncate with an ellipsis and previously had no way to see the full text short of opening the detail modal — added a native title tooltip, set as a DOM property rather than concatenated into the existing (pre-existing, unescaped) HTML template, so it can't introduce a new injection vector.

Added a passive, read-only conflict badge on timeline blocks: calls the exact same checkConflict()/checkVehicleConflict() functions the write-time guard already uses, purely to decide whether to show a warning badge. It never blocks, alters, or duplicates the conflict computation — the guardrails doc explicitly names this pattern as safe.

File
js/timeline.js, style.css

4c — Mobile List-view parity Shipped

.v2-tl-view-toggle — the only control that switches between Timeline and List view — was display: none at ≤767px. List view itself has worked for a while; on mobile there was simply no way to reach it, so every mobile user was stuck on a horizontally-scrolling hour grid regardless of which view suited them. Made the toggle visible and compact instead of hidden.

That surfaced a second, real bug: even fully compacted, the header (title + toggle + date) didn't fit in one row below 380px — confirmed by an actual Puppeteer viewport test, not estimation. Fixed by letting the header wrap to two rows at the narrowest tier instead of clipping.

platform.css

4c — Driver/vehicle/status filter chips Shipped

Added three filter chips above the timeline/list, populated live from getActiveDrivers()/getActiveVehicles(). They narrow the exact same getFilteredAssignments() the search box already used — additive, not a parallel filtering path — so the existing invariant holds: this function feeds display only, conflict-checking still always reads the full unfiltered array.

Native <select> chrome, deliberately — styled to read as a chip rather than built as a bespoke custom dropdown for something the platform already handles well. Verified via real module import (not hand-copied markup): radio-equivalent state, panel switching, and active/inactive chip coloring all confirmed correct in both themes.

05Vehicle / Fleet

5-tab detail drawer

The design map calls for a "5-tab detail drawer." The drawer that exists — vehicle-detail-drawer.js — is a heavily-invested, multi-sprint component (v1.18.4 through v1.29.19) that concatenates ~10-16 sections into one long scroll: Overview, Reminders, Operational, Registration, Tax, Insurance, Maintenance, History, plus an optional Prediction/Simulation block that can add another 8-9 sections on its own. Converting that into exactly 5 tabs meant a real grouping decision, made from the file's own stated conventions rather than invented from scratch.

Ringkasan · Operasional · Legal & Asuransi · Perawatan · Riwayat Shipped

Grouped the existing, unmodified section functions into 5 tabs matching the design map's count, plus a 6th Prediksi tab that appears only when the caller supplies a prediction or simulation — the exact same "omitted entirely otherwise" condition those sections already had, just presented differently. The hero (avatar/score) stays above the tabs as an always-visible header, not tab content.

Built as pure CSS (the checked-radio-input pattern) rather than adding a new JS event listener, so buildDrawerBody() stays what it already was: a pure string builder with zero business logic, matching every other function in this file.

Verified by importing the real module and calling the real exported openVehicleDetailDrawer() against a properly normalized asset (via normalizeVehicleAsset(), not a hand-faked object) — confirmed 5 panels render with the right labels, only tab 1 is visible on open, clicking a tab correctly flips both panel visibility and radio .checked state, and active/inactive tab styling resolves correctly in both themes. An initial 50ms-wait test read mid-transition color values and looked broken; re-checked at 600ms and confirmed everything was correct — worth naming since it's exactly the kind of false negative that's easy to publish by accident.

06Module audit

Warehouse, Overtime, Petty Cash, Engineering, Analytics, Roles, Notifications, Settings

Checked each remaining module against its own line in the design map's per-module table, plus the same three bug classes that proved real and valuable elsewhere this session: a functional control hidden on mobile with no substitute, missing touch targets, and hardcoded content that should read from a live store. A dedicated sub-agent sweep specifically re-checked every CSS file for the "control hidden on mobile" pattern that turned out to be real in the Assignment Board — nothing else like it turned up.

Warehouse — "one workspace shell, 7 tabs" Left as-is, deliberately

Gudang is the deepest, most separately-architected module in the codebase — its own contracts/repositories/projection-engine/audit layers sit entirely apart from its UI, and it already went through its own dedicated LTS audit-freeze. Its actual navigation is a hub-and-drill-down pattern (a home dashboard with cards into Catalog/Goods In/Goods Out/Opname/Analytics), not a single tabbed shell.

Forcing that into "7 tabs" without concrete evidence the hub pattern is actually a problem would risk regressing a considered UX decision, not improving it — exactly the kind of change the brief's own "don't rewrite working structure merely for visual reasons" line warns against. Left alone; touch targets (a deliberate 40px from a recent v1.29.9 accessibility pass, not an oversight) and dark-mode tokens both checked clean.

Overtime — "rate/tier always visible per row" Already true

The records table already has a dedicated "Tarif" column showing tier + rate on every row. No separate button classes exist — Overtime's buttons inherit .btn-primary/etc., which already picked up this session's touch-target and dark-mode fixes automatically.

Petty Cash — "cycle balance above the fold" Already true

The balance is already the primary, most prominent KPI card in the dashboard.

Petty Cash — "NOR draft state added" Already exists, as "Test NOR"

A re-check went deeper than the first pass and found a full, already-built mechanism serving exactly this purpose under a different name. Generating a NOR offers a "Generate as Test NOR" toggle (type: NOR_TYPE.TEST vs OFFICIAL) — a Test NOR doesn't lock its receipts, doesn't affect metrics, and is hidden from official history, with its own amber "TEST ONLY" badge, an "ARSIP · TEST" state when archived, and dedicated convertNorToOfficial()/convertNorToTest() transition functions plus a full archive/restore cascade.

This functionally is a draft state — non-binding, clearly marked, reversible. It doesn't remove the numbering question entirely (a number is still required at generation time for either type), but that's the guardrails doc's own explicit invariant, not a gap.

Engineering — "visually distinct from Driver Ops" Already true

Scoped entirely under its own .eng-root namespace since its original build — confirmed by the file's own header comment stating this was deliberate from day one. Already retargeted onto canonical tokens in this session's Phase 1b.

Analytics — "health score above the fold" Already true

Confirmed the Health Score/Executive Intelligence system exists in js/widgets/executive/ — the product of its own multi-version redesign effort (v1.21.0 through v1.22.6) well before this session.

Analytics — "simulation read-only until explicitly applied" Already true, and stricter

Verified at the code level, not just the UI: js/simulation/scenario-engine.js has zero Firebase/write calls anywhere in the file. The panel itself states this explicitly to the user ("Simulasi bersifat sementara, hanya di memori, dan tidak pernah mengubah data produksi") with a dedicated "Tanpa Perubahan Data" badge and a "Reset Simulasi" action. There's no "Apply" path at all — stricter than "read-only until applied," since nothing ever commits a simulation to production.

User/Role Management — "inherited vs. override visually separated" Already true, and thorough

Found distinct .rm-permission-row--base / --role-additional / --protected classes, each with its own explanatory note text ("Base System Permission — tidak dapat diubah di sini", "Role Additional — diberikan ke semua user dengan role ini", etc.) and a documented tie-break rule for the edge case where a permission is both. This is more thorough than the design map's own one-line spec asked for.

Notifications — "one row component for bell/feed/mobile" Already true, traced end-to-end

renderNotificationsList() already merges the log-derived and server-outbox notification sources into one unified, time-bucketed (Unread/Today/Yesterday/Earlier) list with a single render path. Traced the actual click path to be sure "mobile" really meant the same component: the bottom-nav's notification tab action is literally () => document.getElementById('btnNotifications')?.click() — it simulates a click on the same button desktop uses, opening the identical modal. Not an assumption; followed the wiring.

🚧 Settings — "one settings shell for global/module/feature-flag config": not built

The first pass's claim here was too shallow and is corrected now. Settings are genuinely scattered by module — Engineering has its own renderSettings(), Petty Cash has its own settingsScreen(), each with its own save flow tied to that module's own service layer. Feature flags have no UI at all: loadFeatureFlags() reads /feature_flags once at startup and nothing in the app ever writes to that path — flags can only be changed by editing Firebase directly.

Not implemented this pass, for a reason distinct from the NOR case: this isn't under-specified, it's genuinely two decisions bundled together. A thin navigational shell that links out to each module's existing settings screen would be low-risk and could ship on its own. Building actual in-app feature-flag editing is a different, real security/stability question — which flags are safe to expose to an admin, and what happens if visualShellV2 itself gets toggled off from inside the UI it controls — that shouldn't be decided unilaterally.

Caught before shipping

Three code mistakes, found and fixed mid-session

Worth stating plainly rather than burying: verification caught real errors in this session's own work, not just in the pre-existing code.

🔧 A deletion that would have broken 3 live sites

Retargeting Overtime/Petty Cash's crimson pair, --primary was deleted outright instead of aliased — but 3 sites read var(--primary) directly (not just its -fg/-tint/-hover siblings), which would have silently broken 2 focus rings and 1 active-state highlight. Found by grepping for every consumer before moving on, not by luck.

🔧 A cross-file dependency missed on the first pass

--c-neutral looked dead inside .v2-analytics-claude (zero consumers in that file) and was removed — but js/workspace/workspace-styles.js's Home-workspace widgets are deliberately mounted inside that same scope and read it for 3 live elements (a status dot, a severity-row bar, an icon tint). Restored before it shipped.

📝 A "bug fix" that wasn't one

Claimed to fix a live dark-mode bug in .header and .role-badge — in fact platform.css already overrode both with the exact same tokens and was what actually rendered in production. The code changes were harmless (now-consistent, not contradictory), but the claim was wrong. Corrected the comments to say so rather than let a false "fixed a bug" statement stand in the codebase.

Caught on re-verification

Two claims in the previous version of this report were too shallow

Asked to re-verify the module audit rather than take it as finished, going deeper changed the answer in two places — one from worse to better, one from better to worse. Both are corrected throughout this report now, not just noted here.

✅ Petty Cash NOR draft state — previously called "blocked," actually already built

The first pass checked for a literal 'draft' status string, didn't find one, and stopped there. A second look at petty-cash-service.js's actual generation flow found NOR_TYPE.TEST — a fully-built, richly-designed non-binding NOR state with its own badge, messaging, and conversion lifecycle, serving exactly the purpose "draft" implies. The earlier "genuinely blocked" verdict was a real miss, not a defensible caution.

⚠️ Settings shell — previously called "already integrated," actually scattered

The first pass saw Konfigurasi living inside the admin workspace and concluded settings were unified. That check never looked at whether other modules had their own separate settings screens (they do — Engineering and Petty Cash each maintain their own) or whether feature flags had any UI at all (they don't, anywhere). This is the opposite direction of error from the NOR case: claiming something was done when it wasn't.

Method

How each change was verified

The same four-step discipline ran on every phase, not just spot-checked at the end.

1
Census before touching — grep every consumer of a token or class before changing it, so "safe to delete" and "aliased, not deleted" were decisions backed by a real count, not an assumption.
2
Syntax + brace-balance check after every file edit (node --check, a brace-counter script) — before ever loading a browser.
3
Headless browser check in both themes after every phase — reading actual computed styles from a running page, not inferring them from source.
4
Cross-referenced against the design docs — DESIGN_IMPLEMENTATION_GUARDRAILS, ASSIGNMENT_BOARD_REDESIGN, DESIGN_SYSTEM_SPEC, and RESPONSIVE_BEHAVIOR_SPEC — throughout, not just at the start.
